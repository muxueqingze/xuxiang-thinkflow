# 为什么新成绩不能直接否定旧 benchmark

2026-09-29。用户质疑改造后不如原GitHub benchmark。本次只查历史、源码和已有请求记录，并做无网络fixture；没有新模型调用、没有运行Claude Code/Pro、没有修改运行核心。

## 先纠正评估上的失误

此前新建六道工程题后，没有把原来的前端/小说题保留为版本回归，也没有在同条件下重跑旧核心。报告里的“原轮”是已改造的e49b717第一次六题测试，不是原GitHub 0.5.1。这两轮只能说明e49b717与34119c6在新套题上的表现变化，不能说明34119c6相对旧项目整体提高或退步。

原公开成绩有真实任务依据，应保留：GLM前端中ThinkFlow报告25 calls/757,674token，Claude Code为34/2,663,449；DeepSeek小说分别6/105,576与13/274,974。两模型×两题×两agent共8格，ThinkFlow四格全过，Claude Code四格中三格通过。不能把旧正式结果一概说成玩具题或计量错误，也不能用旧Pi末轮统计缺陷否定这组CC/TF对照。

## 实际变了什么

| 条件 | 原公开正式双题 | 新完整六题 |
|---|---|---|
| 任务 | 完整React前端、长大纲五章小说 | Python修复、重构、协议/状态/边界实现 |
| 对手 | Claude Code | Pi、OpenCode |
| 模型 | glm-5.2 / deepseek-v4-flash标签，旧上游未冻结 | 官方deepseek-flash high |
| 单请求输出 | ThinkFlow请求20,000 | 三方请求8,192 |
| 执行预算 | 每外轮1800秒，最多5外轮 | 全题300秒、24请求 |
| 验收反馈 | validator失败回投同会话，可继续修复 | 完成后隐藏评分，不回投失败 |
| 成功口径 | 文件/build/章节长度检查 | 工程行为检查＋正常终态，主动测试另核 |

原前端大量新文件和小说连续写作，正好提供可预测输出合并的空间；新六题增加必须读取测试结果再处理的工作负载。它们都应保留，但不应替代彼此。旧单任务的7 calls与新12次任务合计108 calls也不是同一个分母。

## 8K确实频繁切断连续生成

从本轮已发布ThinkFlow逐轮usage和终态重新统计：12份样本中9份出现length，共10次；其中7次completion=8192、reasoning=8192、text=0、commands_executed=0。10次触顶合计81,920输出token，其中72,657是推理。这是实际发生的预算截断，不是正常工具反馈要求结束。

原7 vs104快照中，ThinkFlow第2轮报告输出26,174token、执行28条命令、没有传统tool call。快照未保存该轮请求上限，不能由实际输出反推配置；它至少展示了旧优势对应的连续长输出形态。

当前[DeepSeek官方Chat Completions文档](https://api-docs.deepseek.com/api/create-chat-completion/)说明thinking默认输出额度为64K（max effort为128K），[思考模式文档](https://api-docs.deepseek.com/guides/thinking_mode/)说明temperature在thinking下不生效。统一8K/high可作为受限预算测试，但未做预算敏感性验证就将其作为项目核心优化的主要验收，是本次评估选择的不足。不能因此声称换成20K/64K必然逆转排名；应由单变量实测回答。

| API请求 | 108 | 120 |

实际是请求少10%，输出多74.7%，而非工具回合数量全面变差。首请求输入也比OpenCode短，不能只靠“提示变长了”解释全部问题。长思考、截断续写、工具协议选择与反复验证是待隔离的因素；现存数据不能给其中某项分配准确的因果比例。

## 我的改造确有开销和一次错误策略

- e49b717默认隐藏六个原生文件工具，误通道恢复又有缺口。这是后加策略的问题，34119c6已恢复原先首轮可用行为。流式优先仍保留，不应再通过隐藏保底来逼模型走文本协议。
- 0.6让read/bash真正遵循即时反馈边界。两版真实分派方法的无网络fixture显示：旧版可把无need_result的bash和后续write一起排队；新版执行bash后请求反馈，后续write标skipped。这有吞吐取舍，但读取、测试失败是新信息，不能统一改回无反馈执行。
- 0.8增加完整读版本保护、计划schema、环境提示和reasoning回传。离线请求体字符确有增加，但本轮update_plan调用为0，不能拿计划维护解释主要耗量。DeepSeek带tools时官方要求历史reasoning完整回传并拼入上下文，不能为造低用量盲删。
- 首次read_skill要求来自接手前0eeee19；最早开源也已有拉尔夫/todo等工作方法。压缩没有被新benchmark关闭，常规原生回执没有再注入一遍ledger。不能把这些当作已经证实的新增回归。

## “测试有证据6/12”不是旧版到新版的回归曲线

这是本次新增的过程审计，旧样本没有同口径数据。当前两份未执行测试、一份改后未复验、三份最终通过未知，确实需要补强，但不能据此说从旧版完整验证退化到了6/12。最早自动交付验证主要是npm build和粗糙脚本提醒，并不自动完成当前Python公共测试；简单打开旧开关也不能补齐验收闭环。

## 应恢复的验证顺序

1. 保留原前端/小说作为“连续生成”回归组，同时保留新的“读取—修复—验证”组，分别解释适用场景。
2. 在相同当下模型、任务、输出额度、验收规则下比较旧核心和当前核心；d038117/b45c01e只是可恢复代码点，旧报告未固定SHA，不能冒称复原历史运行。
3. 先固定核心，只比较8K与20K或官方正常额度；再固定预算比较核心。若旧核需provider兼容补丁，单独记录，不能悄悄改旧核再称原版。
4. 核心保留流式文件操作与可靠保底，按实际事件定位重复生成/验证；计划等高级能力按需启用，测试结果及修改后的复验作为独立验收条件。

本次没有启动这些新实测，也没有再次扩大API消耗。原数据没有改写，GitHub main经实际查询仍为b45c01e；本次改造留在草稿PR分支，可按具体提交比较和回退。
