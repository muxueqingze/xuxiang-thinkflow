# 2026-09-29 基准差距排查与过程监控

原36次三harness基准保持原样。本轮针对 ThinkFlow 正常交付7/12、用量偏高的原因，检查实际协议与逐轮行为，完成16次受监控的真实诊断。源码修复已完成；没有重跑三方排名、运行Claude Code或安排Pro终审。

## 查到的问题

1. **工具通道纠错缺失。** 模型把 tf-write、tf-edit、tf-write id= 等文本协议名称送入原生函数通道。原代码只报未知工具；原生文件工具又默认隐藏，只有文本解析失败才能开放，误通道没有恢复路径。原版pricing的第7/9/15/16/18/21轮及inbox第7–9轮有直接证据。这不是网络故障。
2. **截断与停止处理错误。** 原生工具开始事件先设置tool_use，后来的length没有覆盖它，未结束参数仍被尝试执行；自动续写额度耗尽可能留下completed。历史unknown副作用回执重放不产生新记录，又可能绕过仅检查新增记录的停止逻辑。
3. **回执引用与Windows命令契约负担。** 长原生调用ID容易造成计划证据反复纠错；cmd.exe与Unix命令混用、tests目录并非Python包、生成测试自身断言错误也造成额外回合。不能把所有失败归为单一协议问题。
4. **完成后的无进展续跑。** 原版pricing产物8/8，却跑到24请求上限；只做协议修复后的inbox第10–22轮仍出现echo/print等空转。成功的无用命令会重置连续失败计数；目前没有可靠的任务语义进展检测。长思考和反复历史输入进一步放大用量。

## 已落地的修复

- 默认从首轮提供原生文件工具schemas，提示仍优先引导可预测的tf-*流式写入。显式enable/allow/deny、授权、FIFO和写前版本检查保持原契约。这撤回了上一轮为推动流式而隐藏保底工具的策略；原取舍缺少真实长链路验证。
- 已知tf-*误入原生通道时，明确告知未执行并指导正确通道；不把错误名称自动翻译后执行。已完成的操作不重放。
- length优先于tool_use，未结束的原生批次整批丢弃，已执行的流式操作保留；续写上限明确标为max_auto_continues/未完成；历史unknown回执重放仍立即停止。
- 成功回执提供稳定短引用receipt:N，计划保存时解析为真实ID。失败回执、重复/冲突alias不能借其他成功记录通关，计数随快照和压缩保持稳定。
- 工具描述明确Windows cmd.exe语义；内置skill不再按改动行数强制额外流程，避免短任务为流程制造占位产物。
- 独立审查发现并关闭监控I/O的P2：监控初始化、事件写盘或关闭失败不能覆盖真实任务结果；错误另记monitor_errors。

## 过程如何被监控

trace.jsonl记录工具通道、输入摘要/hash、命令、状态、错误和每轮usage；live.json每秒更新阶段、上下文大小和思考活动字符数。父runner每8秒显示实际已结束请求的累计token与待usage请求数。最终快照强制落盘，运行中标为running，不能把预置completed当作真正结束。

不保存或展示思考正文。字符计数不是token估算；最终用量由服务商逐请求usage重算。客户端断流后计量代理有限读取usage，避免只统计最后一轮。真实凭据只在本机读取，子进程仅获得本地代理令牌；监控和实验默认不调用模型，必须显式--run。

## 实验结果与决定

全部使用官方DeepSeek Flash high、请求8K、24请求/300秒预算；任务、隐藏验收器和公共测试保护未改。16次均保留，没有择优替换。全部产物8/8，不代表全部正常交付。

同题同次数比较只取pricing与inbox各两次：第一批修复为2/4、75请求、1,844,477 token；原生文件工具从首轮可见为4/4、44请求、1,014,056 token，观察到45.0%的总token下降，仍有14次成功流式文件操作（含edit）发生在同轮流关闭前。采纳这项可用性改动，保留流式优先路径。

**没有采纳状态消息位置改动。** 它保留相同状态和全部reasoning，仅在末条为字符串tool/user时附入该消息；其他形状仍追加user消息。结果未改善收尾，还存在工具输出不再是纯JSON等推广风险。官方示例没有额外user状态，并不能证明它是本次空转原因。

**不夸大四次成功：** 可见性组pricing第1次仅4请求、43,136 token，外部grader全过，但没有bash调用，缺少模型主动执行要求测试的证据；第2次仍需19请求、564,981 token。因此“正常交付”沿用原计分口径，不额外保证工作流程完整。样本数、随机生成和缓存差异也不足以支持稳定收益或领先Pi/OpenCode的结论。

本次实际合计269请求、6,201,161 token：输入5,814,070（缓存5,160,832、非缓存653,238），输出387,091，其中推理224,513已包含在输出。8次客户端断流取得完整usage；全部269请求有usage且HTTP成功。不使用未经核实价格换算现金。之前36次正式基准及连通准备另计，不混入本轮。
