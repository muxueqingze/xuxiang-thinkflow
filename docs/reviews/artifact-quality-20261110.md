# 三题最终产物质量对比 · 2026-11-10

比较固定的12份最终产物：ThinkFlow取`go-stream-final-20261110`，Pi取`go-stream-batch-final-20261110`，每题双方各两次。r1/r2表示两次独立生成。原始产物与计量保持不变，源码见[冻结导出](../evidence/efficiency-20261110/workspaces.json)。

## 具体问题与取舍

- **P2，TF pricing-r2：不需要的兼容和重复舍入。** `checkout.py:10–14,22`与`reporting.py:12–15,26`兼容定价函数返回非Decimal，并重复quantize；题目已明确返回Decimal且每行已舍入，增加了维护分支。`reporting.py:22`还对题目保证存在的tier增加默认值。
- **P2，TF frame-r1：部分附加检查没有有效断言。** 逐字节feed未收集并核对输出，部分检查只打印结果，打印FAIL也不会让进程失败。后来纠正了部分帧的错误自测期望，最终实现通过，但这些检查的判错能力弱于另外三份。
- **P2，Pi receipt-r2：为超出题目范围的精度保留全部金额。** `receipt_tools/model.py:65–109`先收集所有paid金额，再计算动态精度并二次累计。题目有明确规模上限，固定局部Decimal精度已经足够；另外三份能边读边累计。
- **P2，Pi frame-r1：实现路径较复杂且失败后保留载荷。** 完整载荷快速路径与分块路径重复处理解码和终止符，`decoder.py:43–47`失败只改状态。实际接收1 MiB后遇错误终止符，失败对象仍保留1 MiB缓冲；另外三份会释放。仍符合max_size上限，但资源处理和维护性较弱。

额外的数值封装差异：TF pricing-r2的`pricing.py:47`最终quantize位于localcontext之外。调用方将Decimal精度设为6后，题目范围内的大金额会抛InvalidOperation，另三份price_line仍能返回正确金额。题目没有要求兼容调用方修改Decimal上下文，单列这项差异，不改写原契约评分。

## 质量对比

### 票据包

四份均完成金额、校验、CSV和失败保留输出的契约。TF两份与Pi-r1边读边累计；Pi-r2保存所有paid金额，额外内存随收据数增长。Pi两份的JSON错误带实际文件行号，定位体验优于TF：TF-r1只报告malformed JSON line，TF-r2直接沿用单行json.loads的错误信息。Pi-r2与TF-r2的记录校验还带记录索引。

用生成器输入同一客户10,000笔最大规格金额，四份都得到`9999999999999999.99`。仅对summarize调用使用tracemalloc，峰值为TF-r1 6,622、TF-r2 2,930、Pi-r1 2,894、Pi-r2 1,128,426字节；这是单次局部内存探针，不是整个CLI的内存或吞吐排名。结构上的区别明确：前三份只维护客户累计值，Pi-r2额外保存每笔Decimal。

还实际调用四份CLI的CSV生成路径，核对客户名含内部CR的正确引用与csv.reader往返，全部通过。文件写入路径用内存句柄替代，不创建输出文件。

判断：功能相当；TF更稳定地选择了较轻的累计实现，Pi的错误定位更细。Pi-r1同样有轻量累计，不能概括成Pi整体内存差。

### 共享定价

四份均正确处理半分进位、会员/批量折扣、逐行舍入后汇总。动态替换price_line为返回Decimal('12.34')后，checkout和reporting都使用替换结果；没有靠复制公式通过。输入不变性、主要签名、REPORT_FORMAT、客户排序和空订单零金额行成立。

| 产物 | 实现质量 |
|---|---|
| TF-r1 | 局部Decimal精度充分、最后舍入在同一上下文内，整体直接；消费者先格式化字符串再转回Decimal累计，有可省的转换 |
| Pi-r2 | 局部Decimal精度充分、消费者直接累计已舍入的Decimal，职责最顺；两个短格式化函数有少量重复，收益不足以再加抽象 |
| Pi-r1 | Fraction计算并手工舍入到整数分，数学正确；题目规模下普通局部Decimal已足够，数值路径偏重 |
| TF-r2 | 完成题目，但额外兼容非Decimal、重复舍入及量化上下文位置不如另外三份克制 |

判断：TF-r1与Pi-r2接近，Pi-r2的消费者实现略干净；TF-r2和Pi-r1各有不必要的复杂度。不存在稳定的单方优势。

### 增量解码器

独立探针核对全部两段切分、真实换行/NUL/多字节UTF-8、非法UTF-8永久失败，以及bytearray输入后被修改的情形，四份均通过。四份都不会按仅声明的巨大长度预分配载荷。

| 产物 | 实现与验证质量 |
|---|---|
| Pi-r2 | 三状态流程直观，失败、可用性检查、重置职责清楚；失败释放缓冲，直接解码bytearray；保留的测试用断言核对状态和输出，综合最均衡 |
| TF-r2 | 状态机与失败清理清楚，实际附加检查有正确结果参照并在失败时非零退出；保存全部头部数字、解码前复制bytes有可省的开销 |
| TF-r1 | 实现简单，重置和失败集中；部分附加检查只打印、不断言，是主要短板 |
| Pi-r1 | 完整载荷用memoryview快速路径，但与分块路径形成多套分支，失败后还保留载荷；测试本身较扎实 |

在已构造好的1 MiB ASCII帧上，解析期间峰值约TF两份3 MiB、Pi两份2 MiB，与TF解码前额外复制bytes对应。没有测吞吐，不把Pi-r1的快速路径判定为整体更快。

TF-r2的1,100次附加试验包括400次合法流、400次长度上限和300次变异输入；最后一类主要核对异常类型与失败状态，不能当作300个正确输出断言。TF-r1对`b'2:a,'`的错误期望已纠正：feed等待后续输入，finish才应报未完成帧，最终实现未迁就错误测试。

## 综合判断与证据

原冻结结果中12份各通过8组契约检查，双方各6份完整交付；本次实物比较及针对具体疑点的离线探针没有发现新的明确契约失败。代码可维护性、错误定位、临时内存和验证质量存在差异，不能用原8/8或token消耗替代这些维度。

这一轮支持“在这些任务上，以更少token完成同等核心功能”。产物工程质量各有取舍：Pi-r2解析器更均衡，TF票据实现的累计方式更稳定，定价任务双方都出现了偏重实现。ThinkFlow后续工程指引值得改善的是遵守已知接口、少加无需求兼容，以及让必要检查具备有效断言；仍应保持建议可选，不增加强制验收门禁。
