# 生产样本的消耗拆解 · 2026-09-29

## 观察到的问题

- **P2：协议恢复仍消耗整轮生成。** frame_decoder 第3轮把 `tf-write` 当成原生函数名；durable_inbox 第3轮进入流式解析失败分支。两轮都没有成功执行命令，随后才用原生 write 落盘。取消8K截断没有消除这类恢复回合。
- **P2：自建测试的修订和重复验证造成额外往返。** frame 第10轮以后新增 fuzz 并反复修改测试，最后还有一轮重复验证；inbox 第7–10轮只读改自建测试，没有修改生产实现。不能把这些阶段的全部 token 都称为浪费：新增覆盖与修正错误测试都有价值，但反复携带增长历史的成本是真实存在的。

前两案分析 `production-91e4911/{frame_decoder,durable_inbox}-thinkflow-r1` 两个已完成样本，并与 `reports-rerun` 同 id 旧结果比较；文末另补 receipt_package 的唯一新疑点。逐请求重算用量并核对 totals；只查看 meter、harness、trace 的工具事件/测试输出与用量元数据，不读取或公布模型思考正文，不调用模型、不重跑、不修改冻结实现。旧 trace 来自 `formal-recovery-34119c6`。

## 第3轮的协议证据

**frame：确定是原生函数名混用了流式标签。** `trace.jsonl:27` 的 tool=`tf-write`、channel=`native`、success=false，harness 回执错误为：

> [THINKFLOW PROTOCOL ERROR] 'tf-write'是流式标签名/片段，不是原生函数名；本调用未执行。

同轮第二个调用在 trace 第28行因前一个失败而 skipped。第30行用量记录：输入6,225、输出16,689，其中推理12,091，commands_executed=0、tool_calls_traditional=2；meter 该请求67.250秒，以 tool_calls 正常结束。证据足以确认命名混淆；没有保存原始 arguments，不能额外断言 JSON 内容是否正确。第4轮才成功 write decoder.py。整轮22,914 token 是失败轮的消耗，不等于其所有分析都失去后续价值。

**inbox：确定是流式解析错误路径，具体误拒原因未留存。** trace 第23行是 stop，随后第24行错误字符串为“命令格式错误，推理已打断”；第26行记录 abort_reason=tool_failed、commands_executed=0、tool_calls_traditional=0。本轮输入6,364、输出11,851，其中推理9,079；meter耗时47.141秒。

冻结源码 `src/agent_loop.py:1095` 的 parser_error_message 分支把具体解析错误写入内部 messages，只向事件发送上述通用文案。因此现有记录不能还原是哪个标签/参数错误，也不能排除 parser 误拒；不能将其归为 native JSON 解析失败或凭空补出错误片段。最小后续证据改进是保存解析错误类型、通道、位置等非正文元数据，再做离线复现。

旧两份第3轮都在8,192输出、其中8,192推理时 length；新两份允许超过8K，但后续碰到了不同协议失败。这证明旧截断已解除，不证明较长思考导致了协议错误。

## 上下文与因果边界

旧两份没有明确压缩事件，输入 token 和 message_count 没有下降；旧 trace 最大上下文分别137,943/139,074字符、38/40条，均低于旧默认200,000字符/80条阈值。新两份同样无输入或消息数骤降，最大trace上下文208,928/153,823字符，production明确关闭自动压缩。没有证据支持“旧轮压缩过，所以新轮贵”的解释；也不能把生产模式保留完整历史本身归为浪费。

输入计量包括重传历史、工具结果和固定指令，缓存命中提供了大量前缀复用的直接证据；没有逐消息token账本，无法再精确区分每个历史片段的份额。阶段统计是实际使用量，不是移除某个阶段后可节省的严格反事实。两组任务prompt哈希相同、system哈希相同，但首轮工具数由15变14、预算/压缩配置改变，且生成有随机波动，因此单个同id前后比较不能证明取消8K的净因果效应。整体结论等36次结束后汇总。

后续最小改进方向：先补流式解析错误的非正文证据；用离线用例明确区分流式标签与原生函数名，改进协议指引但不猜测执行错误参数；将自建测试断言对齐任务契约，并在最终实现及测试均通过且无新修改后直接结束。先针对上述具体多余回合验证效果，不添加 cap、不删除合理历史、不在本轮冻结运行中修代码。

## 第三案：receipt_package-thinkflow-r2 的成功输出是否丢失

**P2：测试已通过后仍发生多轮低价值探测；没有证据支持“native bash成功stdout被反馈实现丢弃”。** 样本正常 completed、exit0、外部8/8，共24请求、635,185 token、131.734秒，无基础设施错误；有4次流结束前成功delayed写入。本段只补查此疑点，没有重查前两案。

第7轮修自建 `test_large_amounts` 后，trace第61行的bash回执stdout明确为 `Ran 35 tests in 0.753s / OK`。第8–19轮连续12次成功bash，依次包含mkdir/echo done、Python版本/目录、sys.exit(0)/echo ok、读取测试片段、print(1)、echo probe、where python/模块路径、type nul、源码行数、一个金额语义例子、AST解析和读取源码片段；没有生产实现修改。其中部分是有效检查，但print(1)、echo probe、type nul等与已列验收标准关系很弱，不能把整段都称为必要测试，也不能把全部12轮都归为无用。

该阶段实计 **344,761 token（全样本54.3%）＝340,673输入＋4,088输出，其中推理2,665**。之后第20轮再次运行35项测试并得到OK；第21轮写CLI边界脚本，第22轮实际输出13/13通过，第23轮更新计划，第24轮总结。第20–24轮共169,999 token，包含真实新增CLI覆盖，不能整体算作冗余。

对成功输出的定向检查：

- 冻结 `src/executor.py:562` 把捕获结果放入 `ExecutionResult.stdout/stderr`；`src/agent_loop.py:1792` 对bash调用 `_format_tool_result`；第1899行起明确格式化exit_code、非空stdout、非空stderr。
- `_handle_traditional_tools` 第1716行使用该格式化结果，第1750行附近以 `role=tool` 加入messages；正常成功返回不会只留下receipt、丢弃输出。`build_request_body` 保留tool消息内容。两文件与91e4911无差异。
- 将此样本第7/8/12/13/15/20/22轮已记录输出用Mock executor回放，通过真实native反馈函数与MockTransport捕获序列化HTTP请求：**7/7保留完整非空stdout及exit_code:0**。`type nul`确实没有输出，但仍反馈exit_code:0。没有执行这些样本命令，也没有请求模型。
- 原meter全部请求的转发前后messages哈希相同，排除计量代理改写消息；哈希本身不能还原消息正文。原始请求体未保存，因此不能把上述离线复现冒称原轮次抓包，也不能证明模型实际注意或正确理解了输出。

现有证据支持“实现反馈链正常，日志发生了多轮低价值探测”，**不支持判断模型的探测动机，也不支持把成功stdout丢失作为根因**。后续不应为这个未经证实的缺陷重写反馈链。最小方向是：保留该成功stdout→请求体的离线回归；若问题复发，在请求序列化边界记录tool_call_id、输出字符数/哈希等非正文元数据；围绕“35项测试通过后还有哪些明确未满足的验收项”检查计划推进与收尾，避免无新信息的壳探测。仅在出现实际内容丢失证据时修反馈实现，不增加预算截断。
