# 续想的下一步：让执行器核对已知条件

假设用户要求：“配置文件若仍然只有 `draft` 五个字节，就改为 `ready`，然后创建完成标记。”模型已经知道预期正文、替换内容和成功后的动作，唯一未知的是磁盘现在是否符合条件。比较全部字节可以交给执行器。模型在一次生成里声明条件替换和后续写入，执行器在持有目标文件写锁时比较。相等则按顺序落盘；不等则保留文件、停止后续写入，把冲突交给模型。协议见 [edit](../../PROTOCOL.md#47-edit)。这沿用现有版本核对和变更回执，锁的作用域是本进程，与外部编辑器仍沿用原先的写前复查。

另一个场景中，模型只知道要改某个函数，还不知道它的内容。这时执行器读到源码，与模型收到源码，是两个不同的时刻。只有实际请求在压缩后仍带着对应读取结果、且服务端接受了该请求，模型才能用相应版本和范围继续编辑。在同一条流里紧接读取的覆盖命令，不能借用一份尚未反馈的新版本。SDK 的直接读取在调用返回时已经交付给调用者。

## 与 Pi 的对照

Pi 的编辑工具按文件排队并匹配原文片段，支持一组互不重叠的定点替换。ThinkFlow 的 `match="file"` 核对完整 UTF-8 字节，包括 BOM、空格和行尾。Pi 的循环在收到完整 assistant 消息后执行工具并追加结果，支持顺序或并行执行。ThinkFlow 在生成流中执行文本工具，因此还必须维护跨通道顺序：原生工具开始以后到达的文本命令可进入跳过回执，不得越过原生操作先改磁盘。[Pi 编辑工具](https://github.com/earendil-works/pi/blob/ff8721f178fbb5c7ed560ed5c6ba254c5ed425e4/packages/coding-agent/src/core/tools/edit.ts#L147-L192) · [Pi 工具循环](https://github.com/earendil-works/pi/blob/ff8721f178fbb5c7ed560ed5c6ba254c5ed425e4/packages/agent/src/agent-loop.ts#L250-L286)

会话恢复还修复了一条独立路径。原先保存后的历史副本比正式会话更新，内容相同时会排到前面，`/resume 1` 可能把后续保存写入历史副本。现在相同内容优先恢复当前正式快照，独立的旧版本仍可选择。[Pi 恢复入口](https://github.com/earendil-works/pi/blob/275dde410065080d291de45fbe2110272d10de23/packages/coding-agent/src/core/session-manager.ts#L1687-L1700)

## 验证

本地模拟两种供应商的 SSE，执行器使用真实临时文件。指定使用文本协议时，整文件匹配且后续标记落盘需要 1 次请求；原文不符时，文件不变、标记不存在，第 2 次请求拿到冲突。原生工具路径遵循供应商的结果反馈回合。覆盖了部分匹配、空文件、BOM、换行差异、受限文件、撤销、跨通道、压缩、快照恢复和复用回执。

自然语言对照使用 OpenCode Go 的 DeepSeek V4.1 Flash，开启 thinking、high effort、temperature 0，每种组合各一次。Pi 使用本机 1.0.1，旧版 ThinkFlow 固定为 `bb6778e`。每格为实发请求数 / 服务端总 token，包含输入与输出。单条轨迹上限 6 请求，每请求上限 2,048 输出 token。两道首轮题使用开发中的实现；R17 为随后改了协议示例的独立探索题。[题面、初始字节和逐轨迹结果](../evidence/verified-edits-20261118.json)

| 任务 | Pi 1.0.1 | ThinkFlow 0.10.1 | 开发中 ThinkFlow |
|---|---:|---:|---:|
| 两行配置符合预期，替换并写回执 | 3 / 6,210 | 4 / 8,327 | 5 / 10,765 |
| 旧正文不符，保留原件并报告 | 2 / 3,861 | 2 / 3,795 | 5 / 10,803 |
| R17 单行配置符合预期，替换并写回执 | 3 / 7,282 | 3 / 6,149 | 3 / 5,901 |

9 条轨迹全部通过外部字节判定，冲突样本均保留现场并报告差异。首轮题将 `APPLIED` 误写为六个字符，验收以明确的七字节字面量为准。改版的三次运行都没有自行选择 `match="file"`。其中一次即使将该形式加入协议示例，模型仍选择用 Python 比较和写入。两条首轮改版轨迹出现了重复工具 ID，其中冲突轨迹还因工具标记格式多花了一轮。现有记录没有被拒绝的重复调用的参数，无法判定其是否能安全复用。

现阶段，单轮收益已经在真实文件执行路径上成立；在这三个自然语言样本上，没有观察到它带来请求减少。进一步比较应同时记录模型是否选用了相关能力、实际执行回执、请求数和产物。冷恢复后，尚未重新交付的读取仍需要重读或已有附件授权。

## 复跑两个五轮样本

原始记录中，匹配题第 3 轮在思考通道重复使用工具 id，冲突题第 2 轮出现 DSML 正文，第 3 轮在正文通道重复使用 id。当时没有保留被拒命令的参数。复跑在内存中比较参数，只保存相同或不同的判定，并独立检查实际文件、各工具完成时的现场、最终答复和上游用量。

修前的同通道解析器先于执行账本拒绝重复 id。现在，延迟操作进入 FIFO，已执行的同 id 同输入复用原回执，不同输入报冲突。真实重发和真实碰撞在交付版都观测到了。两道匹配题均在第一轮完成 edit 和 write，再用 Python 检查，第二轮交付。冲突题一条在比较失败后又尝试了占用中的 id，再用 Python 核对。另一条在比较失败后同批 read 和 list_files。首个冲突结果已经足够回答原题。

另一条开销来自错误反馈。原实现对完整旧正文不匹配给出“read before revising”，并可能把框架主动中断后留下的半个标签当成模型语法错误。现在回执报告实际条件结果，主动截断保留原工具失败原因。运行时还将思考与正文中的 Markdown 示例隔离于执行路径。在中间候选，反引号里的写入曾创建了禁止创建的标记，又在稍后被删除。另一次仅写成配置、遗漏标记，却被标为完成。此后默认用户界面要求正文交付，配合回执处理仅输出部分命令的情况。

同一题面、模型、生成设置和逐字节判定，每个源码版本和场景各跑两次。每格为每次的实际 API 请求数 / 总 token。

| 场景 | 修前 main (9404f5d) | 交付版 |
|---|---|---|
| 条件匹配 | 3 / 5,866 · 4 / 9,796 | 2 / 3,869 · 2 / 3,565 |
| 条件冲突 | 5 / 11,808 · 6 / 13,646 | 4 / 7,266 · 3 / 4,846 |
| 四次合计 | 18 / 41,116 | 11 / 19,546 |

交付版四次均自行选择整文件条件编辑，HTTP 流正常结束、最终答复与字节判定均通过。两次冲突在工具完成的检查点均保持原件且无标记。修前的中途路径未完整采集。逐次成本、两次中间快照、原题面字符数笔误和观测粒度见[原始数据](../evidence/verified-edit-replay-live-20261118.json)。[重跑脚本](../../bench/efficiency_20261011/verified_edit_live.py)

同一时段补跑 Pi 1.0.1，每个场景各两次。Pi 匹配为 3 / 6,077 和 5 / 11,380，冲突为 3 / 5,994 和 4 / 8,070。四次终局字节和应答均通过。对照的两边各有四次任务，ThinkFlow 共 11 次请求、19,546 token，Pi 共 15 次、31,521 token。Go 提供方报告的额度消耗分别为 $0.00201688 和 $0.00135868。ThinkFlow 输出 3,798 token、命中缓存的输入为 8,704 token，Pi 对应为 1,466 和 21,248。冲突分支两边都用 7 次请求，ThinkFlow 输出 1,966 token，Pi 输出 598。这是接下来可直接测量的开销。单个源代码快照在每道题上只有两次运行，结论仅覆盖这些任务。

实测后仅将新增的 AgentConfig.require_final_response 设为仅接受关键字，已核对原有 19 个位置参数。CLI、桌面和基准工厂均按关键字构造。
