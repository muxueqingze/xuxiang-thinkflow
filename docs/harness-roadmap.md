# 续想：harness 能力地图

2026-09-29。这里区分已经实现、需要补强和未来方向；没有把规划标成完成。

## 续想应该继续坚持什么

「少一次模型回合」只有在没有跳过必要观察时才有价值。继续围绕输出侧的可预测操作建立执行流水线：生成时排队，信息依赖处设边界，用执行回执证实结果。不要把所有 shell、搜索甚至其他 agent 都塞进无反馈队列。

桌面端的价值是让用户看见生成、执行与等待的差别，同时能中止、授权、恢复和核对产物。核心运行时保持可以脱离界面使用。

## 能力与优先级

| harness 能力 | 本版状态 | 下一步有价值的扩展 |
|---|---|---|
| 工具分流与顺序 | tf-* FIFO、信息型 barrier、native schema 注册 | 有明确读写集合后才考虑无冲突操作并行 |
| 失败与停止 | 失败抢占、取消清理、回合/时间/连续失败上限 | 队列背压、按工具资源配额、标准化错误分类 |
| 长程状态 | 原子快照、确定性摘录、会话恢复/分支 | 结构化任务清单、验收证据、显式接力摘要 |
| 副作用可审计 | 命令hash/状态/结果、桌面意图日志、未知状态人工核对 | 内容版本/前置hash、冲突检测、可预览补丁和按文件回退 |
| 人类控制 | 桌面逐次授权、只读/平衡/开放策略 | 操作级capability授权与外部OS容器沙箱 |
| 凭据 | 桌面系统加密、快照/事件不回读密钥 | 多provider凭据与独立credential broker |
| 上下文 | 工作区指引、skills按需读取、历史摘录 | 文件变更感知、检索预算、可追溯来源与过期检测 |
| 模型适配 | OpenAI/Anthropic兼容流、正文可承载tf-* | 能力协商、更多原生协议、流重连策略的provider契约测试 |
| 用户工作台 | Windows desktop、账本、用量、分支、导出 | 文件diff/产物预览、快捷搜索、无障碍与多平台发布 |
| 工具生态 | 本地custom command tools、网络和生图接口 | MCP stdio先行；连接器逐一受相同审批/审计约束 |
| 评估 | 旧benchmark材料、离线调度测试、本地SSE与桌面集成 | 同任务/同模型/同预算的可重复基准，包含失败率与恢复成本 |
| 多agent | 未实现调度器 | 隔离工作区、任务依赖图、合并仲裁、预算、交付验收再启动worker |

## 建议的下一阶段

1. **产物与变更层**：给 edit/write 增加预期文件hash与变更预览。真正防止模型基于过期读取覆盖用户修改。先做确定的冲突拒绝，再做安全回退。
2. **任务与证据层**：任务分解不是把一段计划当聊天文本；保存每项验收条件、状态、产物和验证命令。完成状态由可查证结果支撑。
3. **扩展工具层**：先将一个实际MCP工具接入现有registry，验证超时、取消、授权和大结果截断后，再扩展工具目录。
4. **调度层**：多agent需要独立checkout/进程、依赖关系与冲突仲裁。共享同一目录直接并发写入不构成可靠调度。

以上是基于本项目代码的工程判断，不代表已经实现。两篇官方材料也支持把长期状态、渐进交付和执行边界放在框架层：[长程agent harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)、[Electron安全边界](https://www.electronjs.org/docs/latest/tutorial/security)。

## 应如何证明核心思想有价值

用相同任务分别运行「逐条同步工具」「原生批量工具」「续想流式工具」，保留统一验收与同一环境。比较完成率、错误写入率、总时长、实际输入输出用量、重试次数和人工介入；缓存命中与非缓存输入分列。不要只展示成功样本，也不要把历史供应商返回字段缺失解释成零成本。

优先测试四类任务：批量独立文件生成、读改写混合任务、运行测试后的修复、长输出截断/网络中断。续想最有可能在第一类获益；信息密集任务能否获益需要实测。
